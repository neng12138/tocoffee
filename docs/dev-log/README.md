# 开发日志规范

> 目的：每天结束前做一次可运行检查，并把“做了什么、怎么验证、还有什么问题”写下来，方便第二天和以后回顾。
> 适用：ToCoffee P0 的每个开发日；没有写代码的日子（只调研/设计）也写。

## 1. 文件命名

- 一天一篇：`docs/dev-log/YYYY-MM-DD.md`，日期用本地日期（Asia/Shanghai）。
- 当天对应排期第几天，标题写 `D1`–`D15`，例如 `# 2026-11-05 开发日志（D1）`。
- 进度总表：`docs/dev-log/PROGRESS.md`，每天更新状态和提交号。
- 模板：`docs/dev-log/TEMPLATE.md`，复制后填写，不要直接改模板。

## 2. 每日收尾流程（强制）

每天结束前按顺序执行，缺一项都不算完成当天任务：

1. **冻结代码**：停止新功能，只修当天引入的问题。
2. **跑检查**：按第 3 节执行适用命令；失败先修，修不完就记为阻塞，不能静默跳过。
3. **手工冒烟**：把当天“可演示”的那条路径实际点一遍，记录结果。
4. **写日志**：复制 `TEMPLATE.md` 到 `YYYY-MM-DD.md`，填目标、完成项、验证结果、决策、阻塞、明日计划。
5. **更新总表**：`PROGRESS.md` 的状态改为 `✅ 完成` / `🟡 部分完成` / `🔴 阻塞`，填日志链接和 commit。
6. **一起提交**：代码 + 日志 + 设计/计划变更放在同一个 commit；提交信息用 `feat(dayN): ...`、`fix(dayN): ...` 或 `chore(dayN): ...`。
7. **向用户汇报**：今日完成、验证结果、风险/阻塞、明日计划，四句话以内。

## 3. 检查命令

按当天已有的模块执行；没有的命令写“未到该阶段，跳过”并注明原因。

| 检查 | 命令 | 通过标准 |
|---|---|---|
| 容器 | `docker compose ps` | `tocoffee-postgres` 为 `healthy` |
| API 构建 | `cd apps/api; npm run build` | exit 0 |
| API 单测 | `cd apps/api; npm test -- --runInBand` | 全部通过；无测试时注明 |
| API e2e | `cd apps/api; npm run test:e2e` | 全部通过；未到阶段则跳过 |
| 管理端构建 | `cd apps/admin; npm run build` | exit 0 |
| 顾客端类型 | `cd apps/passenger; npx vue-tsc --noEmit` | exit 0 |
| 空白/冲突 | `git diff --check` | 无输出 |
| 工作区 | `git status --short` | 只含预期文件，无 `.env`、`node_modules`、`dist`、`uploads` |
| 手工冒烟 | 当天“可演示”路径 | 实际点通，截图/URL 记日志 |

Day 1 会加 `scripts/dev/check.ps1`，把能自动化的命令串起来；脚本失败时仍要在日志里贴原始错误。

## 4. 日志写什么

必须写：

- 今日目标（对应计划哪一天、哪几个任务）。
- 完成内容（功能/文件，不贴大段代码）。
- 验证结果（命令 + 结果；失败的贴错误关键行）。
- 决策与偏差（和设计/计划不一致的地方，链接到 spec/plan 的具体小节）。
- 阻塞与风险（没做完的、需要用户回答的）。
- 明日计划（最多 3 条）。
- commit 号。

不要写：

- 流水账（“上午打开 IDE，下午改了 3 个文件”）。
- 大段日志原文；只留错误行/结论。
- 没有验证过的“应该可以”。
- 把问题藏起来；失败和跳过都要写。

## 5. 回顾方式

- 先看 `PROGRESS.md` 的进度和状态。
- 再看某天的日志，定位当时的目标、验证和遗留问题。
- 设计层面的决策看 `docs/superpowers/specs/` 和 `docs/notes.md`；日志只做当日快照，不替代设计文档。
- 发现日志与代码/设计冲突时，以代码和最新 spec 为准，并在当天日志或 `notes.md` 里更正。
